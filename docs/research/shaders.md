# Аудит шейдеров Juiced через x86recomp (офлайн, 05.11.2026)

Игру не запускали. Конвейер: D3D9 bytecode -> `recomp_hlslc` (TranslateBytecode, GLSL) -> glslangValidator (SPIR-V, Vulkan 1.0) -> spirv-val -> spirv-cross (MSL 2.1, те же флаги, что в `shader_compile.cpp`) -> `xcrun metal -std=macos-metal2.1`.
Ветка `juiced-shaders` (worktree `ref/x86recomp-wt-shaders`, от `juiced` fef3d36), коммитов нет: багов с понятной причиной не найдено.

## Итого
- Источник: `effects.dat` (74 .fxo в каждом). Блоки bytecode берутся разбором fxo: ресурсы состояний (usage 0) и строковые объекты (шейдеры-параметры). Первый проход (сканом по маркеру) пропустил 28 шейдеров из строк; исправлено, числа ниже пересчитаны.
- Retail: 137 уникальных; THQ-демо v2 те же 137; Acclaim-демо 2004 даёт ещё 126 других (старые версии). Всего 263 уникальных: 145 vs + 118 ps.
- Версии: vs_1_1 126, vs_2_0 9, vs_2_1 4, vs_3_0 6; ps_1_1 67, ps_2_0 23, ps_2_1 23, ps_3_0 5.
- Prelude: настоящий рантаймовый (`tools/prelude_runtime.glsl`, собран из `Prelude()` в `gpu_device.cpp` скриптом `gen_prelude.py`). Прогон с упрощённым `r_fetch` дал тот же результат, но он мог скрыть сбой; с настоящим сбоев нет.
- Результат: ok 263 / 263 на всех стадиях (транслятор, glslang, spirv-val, spirv-cross, Metal). Падений и `suspicious` нет.
- Размер: максимум 830 токенов (5b3f4b83..., vs_1_1), максимум 102 float-регистра в программе (f5f68c33...), до 6 сэмплеров.

## Статические проверки (на каждый шейдер)
- vs: каждый `dcl` входа (usage+index) есть в `Program::inputs`; записанные oD/oT/oFog/dcl-выходы есть в varyings и наоборот; oPts даёт `writes_point_size`.
- ps: входы v/t (по dcl для ps_2+, по использованию для ps_1) есть в varyings; маска COLORn и oDepth совпадают с записанными; набор сэмплеров совпадает (dcl для ps_2+, dst tex-инструкций для ps_1).
- Константы: максимальный прочитанный `c#` (без `def`) укладывается в `float_regs` и в лимиты 256 vs / 224 ps.
- Инструкции: блоков `r_va` в main не меньше, чем входных ALU-инструкций (пары `+` co-issue считаются одной); потерянной инструкции нет.
- Ручная сверка фрагментов GLSL: `_d2`, `_x2`, `_bx2`, `1-x` (comp), co-issue (оба источника читаются до записи) сделаны верно.

## Гистограммы
Опкоды (всего): dcl 942, mul 775, mad 729, mov 692, dp3 551, add 519, tex 371 (texld/tex), dp4 335, def 206, max 181, m4x4 92, lrp 85, rsq 66, slt 63, m3x3 59, m4x3 51, nrm 39, lit 20, min 19, rcp 16, frc 12, exp 8, cmp 8, pow 8, texcoord 8, dp2add 8, sge 2; co-issue 117.
Модификаторы dst: `_pp` 882, `_sat` 181, shift x2 50, x4 15, `_d2` 6. Модификаторы src: neg 565, bx2 42, comp 34. abs/dz/dw/not нет.
Ни одного циклического/ветвящегося шейдера (rep/loop/if/call/mova/setp/texkill/predicate), ни relative-адресации констант в данных: эти пути транслятора здесь не проверены.

## Пробелы по опкодам
- Транслятор отвергает явно (громкая ошибка, не молчаливый фоллбэк): ps_1_4 и `phase`; в ps_1_x инструкции texbem, texbeml, texreg2ar/gb/rgb, texm3x2pad/tex/depth, texm3x3pad/tex/spec/vspec, texdp3(tex), texdepth, bem; relative-адресация выходов. В данных игры их нет.
- Молчаливое отличие, для данных неактуально: `r_lit` считает `pow(max(y,0),p)` при x>0, спецификация требует y>0 (расходится только при y<=0 и p<=0); `_pp` игнорируется (полная точность); `nrm`, `rcp`, `rsq`, `log` от нуля дают inf/NaN в GLSL, а в D3D9 для умножения 0*inf определено как 0.


## Чего статика не доказывает
- Визуальной и численной корректности: нет эталона, сравнения с D3D9/DXVK по пикселям не было. Перепроверена только структура, а не значения.
- Что рантайм-prelude (`r_fetch` форматы вершин, alpha test, `R_BIAS`) верен по значениям, и что вершинные декларации игры дают все входы VS.
- Клампов ps_1_x ([-1,1] у старого железа), точности `pp`, поведения 0*inf, производительности и регистрового давления Metal.

## Связка VS/PS по техникам (follow-up)
Парсер fxo (`tools/pairs.py`): технические проходы, состояния VertexShader/PixelShader (op 146/147 таблицы OpenJuice), шейдеры-параметры (15 проходов) разрешены через строки. Правила рантайма: varyings по фиксированным локациям семантики (`VaryingLocation`), VS без PS получает PS из `FixedFunctionPixelSource` (читает только varyings VS), PS без VS - fatal.
- Retail/THQ: 188 проходов = 77 VS+PS, 59 только VS (PS генерируется рантаймом из varyings VS: по построению не промахнётся), 52 без шейдеров (fixed-function). PS без VS: 0. Acclaim 2004: 52 / 64 / 51.
- 125 уникальных пар VS+PS по трём архивам. Для каждой создан настоящий `MTLRenderPipelineState` (Apple M4 Pro, MSL из прогона, BGRA8 на число COLOR-выходов, depth32Float, без vertex descriptor; все 263 MSL-библиотеки собрались через `MTLDevice`): 122 ok, 3 отказа. Статический предикат (PS читает varying, которого VS не пишет) выбрал ровно те же 3 пары; Metal: `Fragment input(s) ... not written by vertex shader`.
| техника | где | VS / PS | не хватает |
|---|---|---|---|
| FadeToConstColour (2b03b5c4) | retail, THQ, Acclaim | dd054d19... / 371b66dd... | COLOR0 (PS читает v0.w; VS пишет oFog и oT0, но не oD0) |
| TARMAC_ORIGINAL | только Acclaim 2004 | 9dee2470... / 7589fc97... | COLOR1, TEXCOORD2 |
- Живых блокеров для цели (THQ-демо, retail) нет. FadeToConstColour в рантайме упал бы в `SDL_CreateGPUGraphicsPipeline` (FatalF) при первой отрисовке, но по OpenJuice (`StandardMaterials.h`) единственный материал heathaze01 принадлежит эффекту FRAMEBUFFER, который игра не рисует; TARMAC_ORIGINAL нет в retail/THQ. Считаю спящим дефектом: в D3D9 непишущий VS даёт неопределённое значение, молчаливый ноль не добавлял.
- Если когда-нибудь понадобится: единственная чистая правка - дополнить VS нулевыми выходами недостающих локаций в момент создания пайплайна (знание пары есть только там); в транслятор её не положить.
- Не проверено: что VS-входы покрываются вершинными декларациями игры (нужен запуск), и Metal-PSO для пар VS-только с реальным FF-PS (зависит от стейта текстурных стадий).
